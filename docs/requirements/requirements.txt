2. CONSTRAINTS (non-functional)
-------------------------------
C1  Backend in Flask, data in Neo4j (CLAUDE.md). Server-rendered Flask templates (decision 2026-10-27).
C2  Norwegian and English interface (decision 2026-10-27).
C3  Go-live 1 March 2027 (hard); wedding season from May 2027.
C4  Budget 450 000 NOK incl. 12 months hosting; running cost under 3 000 NOK/month.
C5  Data stored in the EU/EEA; data processing agreement with any cloud/SaaS provider (GDPR note).
C6  Allergies and diets stored per guest group, never per named guest (GDPR art. 9).
C7  Order data kept 5 years for bookkeeping; other personal data shorter.
C8  Customers can request access to and deletion of their data.
C9  Fast pages (Mateo: the old plugin took 10 seconds).
C10 Passwords stored hashed; the Claude API key is never published.


3. FUNCTIONAL REQUIREMENTS FROM basic_desc.txt
----------------------------------------------
Admin side
  A1 Food items: add/edit name, description, price (NOK), minimum order quantity,
     event categories, diet implications ............................ US-18
  A2 Event types: list them, change each one's lower limit ........... US-20
  A3 Images: upload one or more per dish, review before publishing ... US-19
  A4 Orders: list filtered by status and event date; one page per
     order; order status and payment status .......................... US-21 - US-25
  A5 Orders valid against the limit in force when placed ............. US-06
  A6 Reminder 7 days before the event, before the 5-day limit ......... US-11
  A7 Read and answer customers' questions ............................ US-26

Customer side
  B1 Menu cards grouped by event type, with image, price, minimum,
     allergens and diets; minimum from the event type's current limit  US-01
  B2 Cart: add, change, total; orders below the minimum rejected ..... US-05, US-06
  B3 Login based on a unique e-mail; password reset .................. US-04 (reset deferred)
  B4 Submit order: event date, guests, address, allergies, diets,
     delivery notes, payment option .................................. US-07
  B5 Current and past orders visible; past orders read-only .......... US-08
  B6 Cancel until 5 days before the event ............................ US-10
  B7 Ask a question about an order ................................... US-12

Model prompt: event-type minimums are arbitrary placeholders, at most 265 guests.

6. OPEN QUESTIONS
-----------------
Q1 Minimum portions per dish: the system currently requires each dish to reach the larger of the
   event type's minimum and the dish's own minimum (e.g. every dish at least 20 for a Christmas party).
   US-06 only asks for guests >= event minimum and each dish >= its own minimum. To be decided.
Q2 May a submitted (not yet approved) order be cancelled? Assumed yes (state_order.md).
Q3 Placeholder values to confirm with Ingrid: event-type minimums, event times 06:00-23:00,
   earliest event date (more than 5 days ahead).
Q4 Recipes and amounts per portion for the prep list are sample data; Mateo must supply real ones.
Q5 No real e-mail service yet; every e-mail goes to the development outbox.
